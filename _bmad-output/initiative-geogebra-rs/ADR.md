# ADR: Wybór stosu technologicznego (Rust + wasm-bindgen + formulac + symb_anafis) do przetwarzania matematycznego na fron-endzie

| Sekcja ADR                                                                                         | Treść i Decyzje Architektoniczne dla Modułu Matematycznego                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| :------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**                                                                                         | **Przyjęta / Wdrożona**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Kontekst i Problem**                                                                             | Aplikacja frontendowa wymaga wysoko wydajnego silnika do dynamicznej ewaluacji wartości funkcji matematycznych (wykresy/próbkowanie) oraz obliczania pochodnych symbolicznych ze stringów w czasie rzeczywistym, bez generowania zatorów w wątku UI oraz bez narzutu kosztownych zapytań sieciowych do backendu                                                                                                                                                                                                       |
| **Podjęta Decyzja**                                                                                | Zaimplementowanie silnika obliczeniowego w języku **Rust** i skompilowanie go do **WebAssembly (WASM)** przy użyciu biblioteki **`wasm-bindgen`**. Wykorzystanie dedykowanych bibliotek: **`formulac`** do szybkiego parsowania i numerycznej ewaluacji wyrażeń oraz **`symb_anafis`** (`diff`) do operacji symbolicznych                                                                                                                                                                                             |
| **Stos Technologiczny (Kluczowe Biblioteki)**                                                      | • **`wasm-bindgen`**: Most łączący Rust z JS <br>• **`formulac::Builder`**: Budowanie i kompilacja wyrażeń ze stringów<br>• **`symb_anafis::diff`**: Silnik algebry symbolicznej do wyznaczania pochodnych po zmiennej `"x"`                                                                                                                                                                                                                                                                                          |
| **Architektura Komponentu: Ewaluacja Numeryczna (`compute_given_function` & `evaluate_function`)** | • **Parsowanie i kompilacja:** Wyrażenie `expr_str` jest kompilowane raz przy użyciu `Builder`, co optymalizuje proces wielokrotnego liczenia wartości.<br>• **Próbkowanie:** Generowanie 1000 punktów w przedziale `[start, end]` z krokiem `step`<br>• **Normalizacja skali:** Automatyczne skalowanie współrzędnych $X$ i $Y$ do zakresu $[-1, 1]$<br>• **Ekspozycja do JS:** Wyniki są mapowane na instancje struktur `PointResult` (posiadające makro `#[wasm_bindgen(getter)]`) i zwracane jako `js_sys::Array` |
| **Architektura Komponentu: Pochodne Symboliczne (`compute_derivative`)**                           | • Wykorzystuje funkcję `diff(expr_str.to_string(), "x".to_string(), Some(&[]), None)`.<br>• Przetwarza wejściowy ciąg znaków na uproszczoną symboliczną postać pochodnej<br>• Zwraca wynik jako `Result<String, JsValue>`, co pozwala frontendowi na bezpośrednie wyświetlenie wzoru pochodnej lub przekazanie go dalej do ewaluacji                                                                                                                                                                                  |
| **Konsekwencje i Korzyści**                                                                        | • **Wydajność:** Przetwarzanie numeryczne i symboliczne odbywa się z prędkością kodu natywnego bezpośrednio w przeglądarce klienta.<br>• **Bezpieczeństwo typów:** Silny system typów Rusta oraz strukturyzacja danych (`PointResult`) gwarantują bezbłędną wymianę danych z ekosystemem JavaScript<br>• **Skalowalność:** Brak obciążenia serwera                                                                                                                                                                    |

ADR: Wybór stosu technologicznego (Rust + WebGPU) do renderowania wykresów na front-endzie
| Sekcja ADR | Treść i Decyzje Architektoniczne dla Modułu Graficznego (plot-engine) |
|---|---|
| Status | Przyjęta / Wdrożona |
| Kontekst i Problem | Renderowanie tysięcy punktów na wykresach w czasie rzeczywistym przy użyciu standardowego Canvas API (2D) w JavaScript jest zbyt wolne. Bezpośrednie pisanie w WebGL wiąże się ze skomplikowanym kodem i trudnościami w utrzymaniu. Zespół potrzebuje wydajnego silnika graficznego, który obsłuży płynne odświeżanie wykresów (60 FPS) i będzie spójny technologicznie z modułem matematycznym (math-engine). |
| Podjęta Decyzja | Zaimplementowanie silnika renderującego plot-engine w języku Rust, skompilowanie go do WebAssembly (WASM) i wykorzystanie nowoczesnego API WebGPU do sprzętowej akceleracji grafiki bezpośrednio w przeglądarce użytkownika. |
| Stos Technologiczny (Kluczowe Biblioteki) | • wgpu (w środowisku Rust): Bezpieczny i wydajny interfejs do API WebGPU.
• wasm-bindgen: Generowanie wiązań między ekosystemem JS a Rustem.
• winit (opcjonalnie do zarządzania oknem/płótnem z poziomu Rusta). |
| Architektura Komponentu: Przepływ Danych i Renderowanie | • Integracja z Canvas: Silnik podłącza się do elementu <canvas> w warstwie SvelteKit. 
• Komunikacja: Punkty wyliczone i znormalizowane do skali [-1, 1] przez math-engine trafiają do frontendu (JS), a stamtąd są natychmiast przekazywane do funkcji updateGraph w plot-engine.
• Rysowanie (GPU): Otrzymane dane są ładowane do buforów WebGPU, a shadery karty graficznej klienta błyskawicznie rysują odświeżony wykres bez obciążania wątku głównego przeglądarki. |
| Kluczowe Założenia Implementacyjne (Workaround) | • Ze względu na specyfikę obsługi pętli zdarzeń i systemu okien (biblioteka winit w WebAssembly), element <canvas> musi mieć nadane sztywne wymiary w pliku CSS na frontendzie, aby zapobiec anomaliom podczas skalowania i renderowania. |
| Konsekwencje i Korzyści | • Wydajność: Przerzucenie ciężaru rysowania wykresów na procesor graficzny (GPU) klienta gwarantuje maksymalną wydajność i brak zacięć interfejsu (UI).
• Spójność bazy kodu: Utrzymanie obu silników w Rust ułatwia zarządzanie kodem i ujednolica proces budowania (narzędzie wasm-pack).
• Ograniczenia: WebGPU to nowoczesny standard, co oznacza brak wsparcia w starszych lub nieaktualizowanych przeglądarkach. |
